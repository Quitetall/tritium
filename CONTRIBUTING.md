# Contributing to Tritium

Tritium accepts focused fixes, backend ports, estimator research, documentation,
and reproducible model evidence. Start with an issue for changes that alter a
public contract, artifact schema, conformance vector, benchmark claim, or release
gate. Small bug fixes may go directly to a pull request.

## Before opening a change

- Read [GOVERNANCE.md](GOVERNANCE.md) and the applicable ADR or work order in
  the [research repository](https://github.com/Quitetall/tritium-research) (see [docs/RESEARCH.md](docs/RESEARCH.md)).
- Keep dependencies pointing inward as described in the
  [architecture guide](docs/book/src/architecture.md).
- Do not weaken a frozen conformance, quality, physical-byte, or security gate to
  make a result pass. Propose a versioned contract change instead.
- Do not describe compile-only, emulated, synthetic, or structural evidence as a
  hardware, performance, model-quality, or SOTA result.

## Development workflow

Use a focused branch and include tests that fail before the change. The normal
CPU gate is:

```sh
cargo fmt --check
cargo test --workspace --exclude tritium-py --no-fail-fast
cargo clippy --workspace --all-targets -- -D warnings
PYTHONPATH=crates/tritium-py/python pytest -q crates/tritium-py/tests
npm --prefix packages/tritium-web run check
./scripts/check-semver.sh
git diff --check
```

Run only the applicable subset while iterating, then report every gate you ran,
every skipped optional dependency or hardware lane, and every remaining blocker.
GPU, browser, model, package, and deployment claims require receipts from the
declared physical target; a skipped test is not a pass.

## Pull requests

A pull request should contain one coherent change and explain:

1. the user-visible outcome and contract affected;
2. the tests and exact commands run;
3. artifact, model, dataset, device, and source identities for measured claims;
4. compatibility, security, memory, and performance effects;
5. known limitations and follow-up work.

Generated files must be regenerated by their owning script. Do not hand-edit
compatibility tables, release claims, conformance vectors, or evidence receipts.
Never commit model weights, credentials, private vulnerability details, or
licenses you do not have authority to redistribute.

## Design and review

Public API, schema, backend-semantic, governance, and release-gate changes need
an ADR or an amendment to an accepted ADR. Implementations should follow a
reviewed work order in the [research repository](https://github.com/Quitetall/tritium-research). Reviewers verify findings against the
source and evidence before requesting changes; automated review output is not a
verdict by itself.
