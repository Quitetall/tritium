# Ternary PTQ/refinement frontier: October 8 supplement

**Research date:** 2026-10-08

**Comparison baseline:** [ternary-ptq-frontier-2026-10-04.md](ternary-ptq-frontier-2026-10-04.md)

**Window:** new papers/revisions posted 2026-10-05 through 2026-10-08, plus the official Qwen3.8-27B card as a model-selection check. Qwen3.8 was released before this window; it is included only because its official card documents a material architecture and capability change from Qwen3.6-27B.

**Method:** targeted scan of primary papers, author repositories, and the model authors' official sources. No weights were downloaded, no Tritium code was changed, and no Tritium benchmark or reproduction was run.

## Bottom line

This update does not establish that Tritium or any method is SOTA. It adds two concrete release-quality concerns and one kernel candidate:

1. **Hard-code/export parity should be a first-class gate for latent QAT.** A new author preprint reports cases where casting latent weights to BF16 before exporting ternary codes reverses trained code changes and sharply changes task scores. This is not demonstrated for Tritium's PTQ conversion, whose artifacts carry explicit hard ternary planes; apply the lesson to latent-QAT/export and to any path that reconstructs hard codes from lower-precision latent values. Test exact forward-code versus reloaded-artifact parity.
2. **Sparse ternary kernels now have a concrete new CPU candidate.** SSR removes all-zero patterns during preprocessing and reports author-measured gains on CPU, including Llama 3.1 1B. This is an inference-kernel result, not a PTQ-quality result, and does not establish GPU gains or gains for multi-plane additive artifacts.
3. **A Qwen3.8-27B release artifact is materially different from Qwen3.6-27B.** The official card describes a 27B vision encoder model with a Gated DeltaNet/attention hybrid, native image/video support, and MTP. Its table reports improvements on several coding/agentic metrics versus Qwen3.6-27B, but these are Qwen-reported evaluations, not an independent matched Tritium reproduction. Do not silently substitute it for a pinned Qwen3.6 campaign; if the public model-zoo target is intended to be the latest Qwen flagship, explicitly decide and freeze a separate model identity and gates.

## Developments in the window

| Work | New primary-source evidence | Tritium relevance and evidence boundary |
|---|---|---|
| **SSR: Sparse Segment Reduction for Ternary GEMM Acceleration** (arXiv v1 posted Oct 6; DATE 2026 author version) | The authors decompose ternary weights into positive/negative binary planes, then preprocess column blocks into reduced permutations and segment boundaries that omit all-zero patterns. Their CPU implementation uses AVX2, unrolling, blocking, and multithreading. They report 2.1–11.3x GEMM speedup over RSR++ over 45–95% sparsity and 3.5–6.3x end-to-end speedup on Llama-3.1 1B; the paper says the evaluation is CPU-only and notes no GPU implementation. | Relevant to Tritium's runtime/kernel portfolio, not a new PTQ optimizer. It is worth a separately gated CPU-kernel prototype if measured trit sparsity and workload shape are favorable. Multi-plane additive SALT would need per-plane preprocessing and full accounting of indices/metadata, conversion time, resident bytes, and execution overhead. The paper's reported numbers are author evidence on its stated Windows/Ryzen system and its RSR++ baseline, not Tritium reproduction or a cross-hardware result. [Paper](https://arxiv.org/abs/2610.08403), [HTML](https://arxiv.org/html/2610.08403v1), [authors' code repository](https://github.com/fpgasystems/ternaryLLM). |
| **Lost in the bf16 Cast: Exporting Ternary Language Models Can Revert Most Low-Learning-Rate Code Changes** (preprint posted Oct 6) | The authors audit released BitNet, Falcon-E, and BitCPM artifacts and report 0.83–1.77% code mismatch when they quantize shipped latent values in FP32 versus the released deployed codes. In selected fine-tuned endpoints they report severe GSM8K strict-accuracy drops after documented BF16 export; direct code export and an input-projection compatibility route met their stated 4-point non-inferiority margin on the tested rows. The authors explicitly limit the finding to a small recipe family, one or two trajectories per arm, 512 GSM8K development prompts, and specific software versions; they do not claim a general export penalty. | Material release-quality lesson for **latent-QAT**, not evidence that Tritium PTQ is affected. Add/retain a gate that compares training-forward hard codes to codes in the exported-and-reloaded artifact exactly, including threshold ties and actual dtype/operation order. Evaluate the reloaded artifact, not just live latent weights. For PTQ paths that serialize hard planes directly, test that plane serialization/reload preserves them and that scales use the specified deployed precision. Do not adopt the paper's accuracy numbers as Tritium predictions. The paper has no identified author code repository in its primary record; this is a paper-only result and has not been independently reproduced here. [Paper](https://arxiv.org/abs/2610.07853), [full text](https://arxiv.org/html/2610.07853v1). |
| **TACO: Ternary Absolute-max Column-wise One-sparse Optimizer for LLM Fine-Tuning** (arXiv v2 posted Oct 6; initial v1 Oct 1) | TACO chooses a signed maximum-magnitude coordinate per matrix column as the update direction under its stated operator-norm geometry. The revised paper reports, on its experiments, 174x lower persistent optimizer state than AdamW8bit on OPT-13B and full-parameter fine-tuning of 30–32B models on one 80GB H100. | This is a training optimizer/memory research candidate, not a PTQ or additive-code construction method. It may inform Tritium's differentiable training/on-ramp roadmap, but should be an optional optimizer comparison with matched model, data, quality, and runtime gates—not folded into the PTQ result. Author paper and code are available; claims remain author-reported. Since v1 predates the comparison baseline, this supplement records the **Oct 6 revision**, not a claim that the work first appeared after Oct 4. [Paper v2](https://arxiv.org/abs/2610.02199), [HTML v2](https://arxiv.org/html/2610.02199v2), [authors' code](https://github.com/Jichao2357/TACO_optimizer). |

## Qwen3.8-27B model-selection check

The official Qwen project says Qwen3.8-27B became available on Hugging Face and ModelScope on **2026-08-14**, before the literature window above. Its official model card identifies it as a 27B causal LM with a vision encoder, 64 language layers in a repeated Gated DeltaNet/FFN and Gated Attention/FFN layout, MTP, native 262K context, and image/video understanding. This is a material architecture/modality change relative to treating the name as a mere Qwen3.6 repack. The card's own table compares Qwen3.8-27B and Qwen3.6-27B and reports higher Qwen3.8 scores on several coding/agentic rows (for example Terminal Bench 2.1: 73.0 vs 63.4; SWE-bench Pro: 61.7 vs 53.5), while not winning every listed metric (for example GPQA Diamond: 89.2 vs 87.8, below the listed Qwen3.7-Plus result). The card provides some evaluation protocol notes, but these are model-author results, not independent validation.

This matters to the release's model-zoo and campaign identity, not as proof that Qwen3.8 ternarizes better. The 2026-10-04 frontier note's Qwen3.6-27B campaign should remain tied to its pinned source/model until its gates finish or an authorized scope amendment explicitly creates a Qwen3.8 campaign. If public release policy means the showcased artifact must be based on the then-current Qwen family release, record a separate model-choice decision before allocating compute; Qwen3.8's vision encoder also creates additional multimodal conversion/runtime gates outside a language-only result. [Official Qwen3.8 repository/news](https://github.com/QwenLM/Qwen3.8), [official Qwen3.8-27B model card](https://huggingface.co/Qwen/Qwen3.8-27B).

## Recommended test and research treatment

1. **Export correctness (release gate candidate):** for every latent-QAT path, compare hard code tensors before export with codes observed from the reloaded artifact. Include exact-threshold and adjacent-representable-value fixtures across source and deployed dtypes, tied values, scale recomputation, save/reload, and each supported export route. Store deployed-code digests. A mismatch is a functional failure even if a floating-latent validation score looks good.
2. **PTQ artifact replay:** for the public `prepare → calibrate → convert()` route, test the actual saved/reloaded model against the converted in-memory hard model; separately validate scale-rounding and packed plane/code parity. Keep hard-code fidelity distinct from approximate output parity.
3. **SSR prototype only after a kernel baseline:** compare its preprocessing metadata and resident memory against Tritium's current CPU kernel and sparse baselines on the same matrices, batch/prompt shapes, trit sparsity, compiler, and CPU. Measure preprocessing, cold/warm execution, decode and prefill separately. Reject it if metadata or indirection erases the speed/space win. Do not infer GPU performance from the CPU paper.
4. **TACO optional training comparison:** if the release's differentiable training scope includes full fine-tuning, compare TACO with the selected PyTorch optimizer on frozen model/data/steps, reporting quality, optimizer state, peak memory, wall time, and hard-artifact export parity. Keep it separate from PTQ/refinement conclusions.
5. **No SOTA promotion:** existing frozen gates, independent reproductions, exact physical-byte accounting, held-out quality, and per-device runtime remain necessary. These new papers provide hypotheses and an additional export-fidelity concern; they do not establish a Tritium win or warrant relaxing a gate.
